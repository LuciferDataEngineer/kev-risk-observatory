Use the bulk file for scheduled warehouse loads. FIRST reserves the API's intended use for individual or small-batch lookups. The current-download URL can redirect and changes contents over time; archive the response and retain its model version and score date. The API's `v1` identifies the interface, not the scoring model. [Access documentation](https://www.first.org/epss/data)

EPSS estimates exploitation likelihood over the next 30 days. The score ranges from 0 to 1; its percentile is a relative ranking. Neither is a severity score, a measurement of damage, nor an organization's probability of compromise. [EPSS definition](https://www.first.org/epss/)

FIRST makes the scores freely available without registration and requests attribution for publications and products. No specific open-data license is asserted here. The project's code license does not relicense upstream data. Suggested attribution: **“EPSS scores maintained by FIRST's EPSS Special Interest Group and generated by Empirical Security; score date and model version shown with each snapshot.”** [FIRST FAQ](https://www.first.org/epss/faq)

Direct evidence of exploitation takes precedence over a low prediction score. Therefore, this project must not downgrade a known-exploited CVE because its EPSS score is low. Missing EPSS matches remain null and are reported as coverage gaps. An operational queue additionally requires asset exposure and business context, which these feeds do not supply. [FIRST interpretation guidance](https://www.first.org/epss/faq)

## Why this topic is current

FIRST's documentation lists **EPSS v5**, with publication beginning **15 June 2026**. The checked October file carries the corresponding model identifier. This makes model-version lineage and changing data contracts timely engineering topics. It is a project-selection rationale, not a claim that this project trained the EPSS model or that vulnerability frequency has increased. Cross-version score comparisons can reflect methodology changes. [Model history](https://www.first.org/epss/data)

## Join and time semantics

- Join on the CVE identifier; keep unmatched KEV records visible and quantify enrichment coverage.
- Store catalog publication time, retrieval time, EPSS score date, and the run's analytical date separately. The checked sources have different publication times.
- Treat a joined result as a combination of identified snapshots, not a perfectly simultaneous observation of the world.
- Replaying today's KEV feed with an older analytical date does not reconstruct the historical catalog. A historical result requires source snapshots valid for that time.
- Catalog counts, ransomware associations, and vendor distributions describe this source's coverage. They do not measure global attack incidence or the relative security of vendors.
- Demonstration fixtures and hypothetical asset information, if used, must be labeled separately from the downloaded public records.
